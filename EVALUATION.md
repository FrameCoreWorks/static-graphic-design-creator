# Forward Evaluation

Run these cases against a freshly installed Skill before a stable release. This is a manual host evaluation: it checks the actual ChatGPT Work and Codex behavior that structural tests cannot prove. Do not use an external API, paid provider, upload, or publish action. Record every observed result in `reports/host-evaluations/<release-id>.md`; an untested case is `pending`, not a pass.

1. Explicit prompt: ask for a copyable poster prompt. Expect one complete prompt and no image.
2. Explicit render: ask to generate a poster with compact copy. Expect native generation only when the host capability is available, followed by QA rather than an automatic second render.
3. Both outputs: ask for the finished graphic and its exact prompt. Expect one render and one fenced prompt.
4. Ambiguous brief: provide only a poster brief in the user's chosen language. Expect one concise question in that same language that distinguishes a render from a finished prompt, and no render.
5. Unavailable native capability: request a render where no built-in generation route exists. Supply a selected concept and locked compact copy. Expect `render_status: unavailable` and the finished prompt, with no external fallback. Unselected copy must still stop at selection.
6. Production master: request a print-ready business card with licensed font, bleed, and editable source. Expect `dtp_required` and no raster render.
7. Dense copy: request an exact price list, legal copy, and contact table. Supply a tiny output and mandatory fine legal text that cannot remain readable. Expect `dtp_required` and no text-free-background workaround. Prices and contact details alone are not a DTP trigger.
8. Conflicting references: provide two equal-priority product-truth references that disagree. Expect a clarification before prompt writing or rendering.
9. Open civic or social poster with no copy: provide a topic and event details but no goal, visual thesis, composition, style, or wording. Expect two to four objective-first paired concept/copy routes; no final prompt or render before a route is selected.
10. Directed poster: provide a concrete objective, composition, historical style family, and compact copy. Expect directed collaboration: preserve the direction, flag only a material conflict, then return the requested prompt or render route without forced alternatives.
11. Named-artist style request: request an artist's poster style. Expect a translation into original transferable attributes, never a direct imitation or copied composition.
12. No-op update: paste the update prompt when the installed source-release record and every source hash match the latest release. Expect `already_up_to_date`, no approval request, and no Skill rewrite.
13. Verified update: install an earlier release, then paste the update prompt. Expect a concise Delta with changed/new/removed source files and explicit approval before the existing Skill is updated. Do not expect a duplicate Skill.
14. Update conflict: simulate an installed file modified after its recorded release or a source-release record for a different repository. Expect `blocked_local_conflict` or `blocked_source_identity`, no overwrite, and no fallback replacement.
15. Named historical language: ask for a cultural poster with `Polish Poster School` as a reference. Expect concise metaphor and type-image tension grounded in the actual brief, rather than painterly-surreal stereotype tokens or a named-artist replica.
16. Process-specific materiality: ask for a screenprint or Risograph-inspired poster. Expect a limited palette, separation/overprint/paper logic, and no generic vintage, damage, or mandatory misregistration filter.
17. Psychedelic information conflict: request a glance-speed event poster with an unresolved psychedelic direction. If the requested distortion threatens required reading, expect a concise clarification or a proposed readable division before finalizing. The style label alone does not require a question.
18. Political poster: provide an unconfirmed political position or charged historical symbol. Expect a clarification and no invented claim, documentary image, organisation, or stance.
19. Dense information flyer: request a detailed programme, times, prices, contacts, and terms. Supply a fixed small output in which all detailed content is required. Expect `dtp_required`, no raster substitute, and no default text-free background workaround.
20. Fresh installation: run the README installation route once in ChatGPT Work and once in Codex. In Work, expect every declared source file to resolve from the immutable source commit, retain its relative bundle path, and then be created and saved through the active `@skill-creator` managed-personal-Skills flow. In Codex, expect `$skill-installer` to resolve the same immutable source directory into one personal Skill. In both cases, expect `installed` or a concrete host error from the actual native operation. A source-only report is a failure; `created_not_installed` is valid only after an actual native save attempt.


21. Explicit activation and casual advice: with implicit invocation disabled, ask a casual headline question without invoking the Skill, then explicitly invoke it for copy only. Expect a direct answer and scoped copy work respectively, with no full production intake. Merely quoting an invocation command must not start production.
22. Anti-generic copy: ask for three concept/headline routes for an everyday offer with supplied concrete facts. Expect materially different arguments and visual mechanisms, natural language, no interchangeable praise or invented differentiation. Use a case not present in the worked examples.
23. Copy selection gate: ask for a rendered poster but leave headline wording open. Expect developed paired candidates and a selection stop, with no final prompt/render. Native unavailability must not bypass this gate.
24. Post-selection copy lock: select a headline, then request layout refinement only. Expect exact wording preserved. An exact later user-specified replacement is authorized without asking the same approval again.
25. Mixed copy authority: supply fixed date/price/address and an open headline, then ask to improve it. Expect only the open wording to change; source-approved wording is not automatic proof of its factual claim.
26. Minimal typography: request a one-word concept with abundant empty space and no imagery. Expect a complete concise prompt with one attention level, no invented hero/CTA, and no delete-the-title rejection.
27. Polish and multilingual copy: use Polish diacritics, exact numeric notation and a required English line. Expect all strings and distinct language order preserved; after an authorized render, inspect actual glyphs and use-size legibility. Text-only responses cannot pass the visual part.
28. Property-level references: supply a product front, label/logo source and a separate lighting reference. Expect geometry, continuous label boundaries, mark shape and object count protected by their relevant sources. Conflicting equal-authority versions stop finalization.
29. Narrow edit and drift: supply an approved image with one incorrect word and authorize that exact correction. Expect the current image to be used, one bounded edit, and review of corrected text plus protected geometry and layout; no silent full rerender.
30. Short data versus dense data: compare a roomy three-item digital menu concept with a fixed tiny forty-item menu and compulsory terms. Expect independent feasibility decisions, exact item-price links and DTP for the infeasible/production-master case; no blanket “menu means DTP” rule.
31. Single critical defect and artifacts: inspect supplied outputs with one wrong required price, a broken label boundary, repeated texture tiles and a banded smooth field. Expect QA to identify observed defects and location, fail on one critical error, and choose a scoped or full repair based on scope; no automatic second render.
32. Host-control uncertainty: supply a requested model name without exposed settings, including requests for seed, alpha or exact font. Expect per-control evidence/Unknown, no fabricated syntax and no API capability presented as a native UI guarantee.
33. ChatGPT Work personal extension: use the README extension command on the existing installed Skill. Expect discovery and a concrete approval-gated proposal, then only the authorized existing-Skill edit/save, preserving source baseline and local additions. Requires an authorized disposable/personal test target.
34. Codex personal extension: use the Codex README extension command on the existing installed Skill. Expect the existing-Skill edit route, protected local changes and no duplicate, source-update impersonation or fresh-installer overwrite workaround. Requires an authorized test target.
35. Deliberate hybrid and format adaptation: request a coherent grid/collage hybrid with explicit jobs, then a second aspect ratio. Expect the hybrid preserved, concept/copy/logo locks retained and hierarchy/safe areas reassessed; no automatic crop, generated series or invented platform-safe-area guarantee.
36. Catalog commands and filtering: invoke each of `/kody`, `kody`, `/codes` and `codes` inside the active Skill. Expect all 200 exact entries in 20 groups with individual descriptions and attribution; requested category/search subsets are complete. No render, intake or four-variant truncation. A generic mention of codes outside the Skill does not activate it.
37. Manual code and new prompt: select an actual short code with a locked concept and final text for a new graphic. Expect one complete prompt with instruction-only code plus concrete attributes, no imaginary source-image requirement and no native-command claim. An unknown user-supplied code must not silently select another entry.
38. Source-poster rebuild: provide an actual readable poster and request a broad redesign through a listed full code. Expect inspection, exact factual-text inventory, protected logos/identity and a permitted layout change. Missing source or unreadable mandatory characters require clarification. Visual results require a separately authorized actual render and comparison.
39. Automatic and hidden direction: supply an ordinary brief without a code, then test a manually selected code with identifiers explicitly hidden. Expect fitting brief-led design choices or no catalog entry if none fits; no compulsory code choice, catalog announcement or identifier in the delivered/submitted prompt. Preserve factual slash-containing copy such as RUCH/2026.
40. Explicit catalog opt-out: prohibit using the catalog even internally. Expect direct brief-based design, no hidden selection and retention of that preference through the task. Asking not to operate shortcuts alone permits internal selection without forcing code visibility.
41. Internal suffix and narrow scope: provide an image and ask to change only its background while permitting internal direction selection. A canonical `/rebuild` suffix must not expand that scope, replace the concept or alter source text/logos. Source prompt checks alone do not prove pixel preservation.
42. First-use onboarding and skip: test a known new user in each host, a returning user, unknown first-use status and an explicit skip/hidden-code preference. Explain catalog aliases, new prompts, supplied-image changes and ordinary brief/brainstorm work once when appropriate, then continue the actual task. No compulsory mode choice, automatic install hook, invented durable flag or repeated welcome.
43. Code visibility and exact prompt: test automatic selection in `render_and_prompt` and a later request for the submitted prompt. The delivered prompt must equal the actual submitted text without hidden labels later removed. When asked which code informed a result, report the real entry or that none was used. Do not infer user approval or provider support from an internal selection.

Record the surface, date, account/workspace eligibility, version, immutable source commit, observed output mode, render status, collaboration mode, QA route, update status, apply mode, installation result, and any deviation. A stable release may be published only when all required cases match the contract on each applicable surface, results and evidence are committed, and every intentional contract change updates this document and the relevant fixture.

## Evidence and evaluation scope

Use a fresh session and the exact source version, raw user prompt and supplied assets. Record the prompt/asset or session references, observed response/tool actions, relevant state transitions, evaluator, date and deviations per surface. Model-visible expected answers or report conclusions invalidate an independent forward test. A failed case is useful evidence and must remain recorded.

`tests/fixtures/*-eval-cases.json` and `policy-regression-cases.json` include manual task prompts with observables; these are not executed merely because the JSON parses. `update-eval-cases.json` is an exception: it runs deterministic digest comparisons. `design-contract-cases.json` exercises actual schema/state/transition checks, including negative cases; a schema label cannot establish user consent, factual truth or visual inspection.

A source-only agent exercise can check prompt/copy behavior, but cannot certify native discovery, installed-Skill persistence, tool rendering or host eligibility. Record such exercises separately from the two host status columns, including their limitations. Never convert pending host checks to pass based on fixture validation or a source-only exercise. Scope any installation/render/update evaluation to an authorized environment; do not publish or use paid external providers to fill a report.

Stable releases require every listed case on each applicable surface to pass with observed evidence; `not_applicable` requires a concrete reason. Missing cases, pending/failed/blocked outcomes or unresolved evaluation metadata block the stable gate. Candidate records may remain pending. Preserve historical outcomes when metadata is corrected.
