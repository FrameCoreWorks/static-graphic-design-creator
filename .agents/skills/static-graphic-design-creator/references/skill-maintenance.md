# Installation, updates and personal extensions

Read this reference for Skill maintenance, source-versus-personal differences or an approved extension. Maintenance never starts design production. The user's chosen destination governs: repository work changes repository sources; an installed-Skill task uses the active creator for that same existing Skill. Neither destination silently authorizes editing the other.

## Source identity and actual content

`references/source-release.json` names the upstream base, not the newest similar feature set. A personal extension preserves this record; it cannot claim a release that has not been applied. A verified upstream update replaces the record in the same proposed result as all approved source changes and safe removals. Never advance only the record to conceal unresolved conflicts.

Three Git IDs may legitimately differ: the commit containing the source files, the later commit containing the manifest that hashes those source files, and the host's save commit. Compare file hashes against the declared **source** commit. Do not require these three commits to be identical or use the newest commit indiscriminately in source URLs. A clean Git working tree only means no uncommitted edits; committed personal changes still differ from upstream.

Keep installation evidence in a real host-supported receipt/history outside the canonical upstream files: Skill identity, upstream release, immutable source commit, immutable manifest commit and digest, upstream file digests, actual saved file digests, extra/deleted/modified paths, approved resolutions, save/readback result and rollback reference. Do not include credentials or unrelated private content. A receipt describes observed evidence, never creates proof of an unexecuted save, and must not hash itself. If durable evidence is unavailable, report that limitation and retain the upstream record for baseline resolution.

## Existing-Skill updates

Follow the repository's current `CHATGPT_UPDATE.md` or `CODEX_UPDATE.md` after resolving their discovery commit. The [read-only lifecycle helper](../scripts/skill_lifecycle.py) verifies two retrieved source bundles against their manifests, compares them with the installed files and emits conflict previews. It cannot fetch, install, overwrite, save, publish or grant approval. A host without Python follows the same byte/digest algorithm and reports any verification limitation.

Prepare a complete proposed resolution during the read-only comparison; no separate user approval is needed to inspect files, compute differences or prepare an in-memory merge. For a new upstream path also created locally, the old baseline is **absent**: review both additions, rather than inventing a common ancestor. Distinguish files already equal to the target from actual outstanding differences.

For wording-only provenance differences, propose adopting the target's release wording and explain the exact change. For real personal behavior, propose a reviewed merge or retain it as an explicit local deviation. Do not infer equivalence from a filename, a style count or similar behavior alone. Never silently discard differences because a merge tool reports no conflict. Show all resolved changes, remaining deviations and preserved assets for one approval before saving. If an actual behavior choice cannot be resolved from the brief, ask that specific question with the alternatives already prepared.

An unresolved conflict blocks the **entire update**, including otherwise safe files and the source record. Recheck the installed snapshot and pinned target before the approved save; concurrent changes invalidate the proposal. Verify the complete resulting inventory, bytes, source record, safe deletions and retained local files after the actual host save. Use the evidence-based save/recovery procedure below before retry or rollback; a failed response alone does not establish the saved state. A second comparison after a successful update returns `already_up_to_date` for an exact copy or `local_customizations_preserved` for the recorded personalized result.

## Personal extension storage

Use the active creator on the existing Skill only. First inspect the relevant current files and clarify the desired behavior; prepare concrete changes and obtain any required approval before writing. Preserve the installed upstream record. A personal extension is not a source update or a new release.

Prefer `local/SKILL_EXTENSIONS.md` as the entry point for approved personal instructions, with supporting assets/data under `local/`. This namespace is reserved for personal files and excluded from public releases. Create it only when an actual extension is requested; no empty placeholders are installed. Keep the extension self-contained and scoped to the user's requested behavior. Runtime instructions in SKILL.md discover this optional entry after explicit activation. A missing local entry is normal and requires no question or new file.

In that entry, record the feature purpose, approved behavior and relevant local resource paths. Keep change/evaluation evidence in actual host-supported history; if a local extension record is used, treat it as personal data, not a new source manifest. Never copy personal files into a public repository as part of ordinary release preparation.

An extension can require a canonical-file change when the optional entry cannot implement the requested behavior. Explain that reason, capture the previous and new bytes/digests and retain it as a tracked personal override; do not promise conflict-free future updates. Existing extensions embedded in upstream paths are not automatically moved or deleted. During a later approved update, migrate the actual personal behavior to `local/` only when the proposed integration preserves its meaning and avoids duplicate or contradictory execution. Host metadata and icons also remain explicit local differences, not ignored verification exceptions.

Local instructions do not override the current user's explicit brief, factual/reference locks, safety requirements or execution permissions. When a local extension conflicts with a new source contract, report the concrete incompatibility and resolve it before using that part of the workflow. Do not load unrelated personal assets or run local scripts merely because they exist.

## Save evidence, recovery and resumption

Use this procedure for an approved existing-Skill extension or source update. The active host's creator determines the actual destination, save mechanism and reconciliation/readback. Do not impose a ChatGPT storage branch, Git transport or delay on Codex. These are workflow states, not host API values: `proposal_approved`, `prepared_local`, `validated_local`, `save_attempted`, and then a result established by readback. Validation, a local commit, a UI entry, a successful-looking message or an acknowledgment alone cannot establish persistence.

Before the first write, retain the complete pre-change Skill and build the complete intended result, with exact approved additions, replacements and deletions. Bind the approval to those bytes and the existing Skill identity. Include the source record and all unrelated personal files in both inventories. For a personal extension the source record must remain byte-identical; a source update must equal its verified approved target record. Immediately before saving, compare current saved state against both snapshots. If the intended result is already present, verify and stop without claiming this attempt created it. Any other change from the approved baseline is `inputs_changed` before a save has been attempted and requires a fresh Delta; preserve the newer state and never replay an old whole-tree commit over it.

After **every** save attempt, including nonzero exits, HTTP 5xx, disconnects and lost responses, perform the host's supported bounded reconciliation/readback. Read the complete saved inventory and bytes from that host, not the prepared working copy or a cached Skill listing. Keep transport outcome separate from content outcome:

| Observed complete saved state | Result and next decision |
| --- | --- |
| Exactly intended, including preserved files | `saved_verified` after an attempted change, even if the response was lost; no retry or rollback. If already present before any attempt, use `already_present_verified` and make no new-save claim. |
| Exactly baseline, with an outstanding approved change | `save_failed` after an attempt; no remote rollback. For an observed transient error only, consider at most one retry after the first attempt and a fresh complete readback, within existing approval and any stricter host limit. After two attempts, stop and preserve the prepared work. |
| Partial, different or unexpectedly extended | `save_mismatch`; list missing, extra and changed paths. Do not infer who changed them from hashes alone. Preserve observations and review a repair or rollback using the supported host workflow and the authorized scope; protect later changes and verify any recovery result. No automatic whole-snapshot restoration. |
| Unavailable or not known to be complete/current | `verification_unavailable`; state the last verified observation. Do not infer failure or success of persistence, retry blindly, or perform a blind rollback. |

Classify a non-fast-forward rejection separately: reconcile through the active creator's supported procedure, then revalidate the approved content and preserved files before another save. Do not use rebase as a general response to HTTP 500, force-push, change hooks/permissions, switch to another service or create a duplicate Skill. An HTTP 500 establishes an observed service/transport error, not its root cause or a content-format restriction. A successful response with a baseline readback also fails verification once supported reconciliation checks are exhausted.

The [read-only lifecycle helper](../scripts/skill_lifecycle.py) offers `inspect-save` in addition to its existing source-update comparison. Supply complete `--before`, `--intended` and `--observed` directories, repeat `--approved-path` for each changed/new/deleted path, and record `--attempts` and `--save-outcome` (`acknowledged`, `transient_error`, `rejected` or `non_fast_forward`; zero attempts uses `not_attempted`). Default `--operation personal_extension` enforces an unchanged source record; `source_update` diagnoses an already verified source-update proposal. Omit `--observed` only when readback is unavailable; an empty directory is an observed empty result, not missing evidence. The helper checks paths/bytes and recommends a next review, never performs host operations or proves consent, readback provenance, durable storage or public-release integrity. Exit 0 means the supplied observed snapshot exactly matches the intended result; exit 1 means it does not establish completion, and exit 2 means invalid/unreadable input. Without Python, use the same complete inventory/content comparison and disclose unavailable verification.

Before ending a failed session, verify what prepared work remains accessible. Preserve the approved patch or complete new files plus original bytes needed for replacements/deletions, target identity, approval/scope evidence, before/intended/readback digests, observed error and attempt count, and last verified host state in an actually supported private recovery location. Hashes alone cannot reconstruct content. Keep this material outside the public repository and upstream manifest; do not create a second Skill or use an unsupported storage route. Verify a supported durable checkpoint by reading it back. If only the working checkout/scratch remains, say that independent durable recovery is unverified; never call a temporary path a backup. Do not erase prepared work just because a remote save failed.

On resumption, check that the recovery contents still exist and match the approved result, then reread the current host state. Do not reset the attempt count to bypass the retry limit, assume scratch survived, recover from hashes alone or overwrite later edits. Missing recovery content calls for recovering the actual files or reconstructing a reviewable proposal with the user; a remembered feature description is not the formerly approved patch. Report local preparation, observed persistence and recovery availability separately. An unchanged remotely verified baseline needs no remote rollback. A failed attempted restoration is `rollback_failed`; an unobservable restoration remains `verification_unavailable`. A later user-authorized retry may establish a new bounded attempt window after fresh comparison, without pretending prior failures did not occur.

## Layered-workflow compatibility

Public layered-asset capability and a personal preference may coexist. Inspect the actual local instructions for overlapping generation cadence, version selection, packaging or DTP scope. Preserve nonconflicting preferences, honor the current user's brief, and resolve a concrete semantic conflict before that operation; file-level non-overlap is not proof of runtime compatibility. Never copy personal layer registries, project images or approval histories into a source release. Active project records live with the project, not in `local/SKILL_EXTENSIONS.md`.
